## 供应规则（本轮补齐）

配置位于 `parameters.supply.rules`，旧夹具全部为 `[]`，因此不产生任何自动需求或消费。规则为纯配置、无价格、无 UI：

```ts
interface SupplyRule {
  id: EntityId;
  sourceNodeId: EntityId;      // 发货运输节点
  destNodeId: EntityId;        // 收货/消费运输节点
  ownerId: EntityId;           // 需求、货款与两端库存的所有者
  purpose: Purpose;
  cargo: 'grain' | 'materials';
  targetStock: LoadUnit;       // 目的地目标库存
  consumptionPerTick: LoadUnit;// 每旬实际消费上限
}
```

默认 `loadClass` 取 `'standard'`，需求 `deadlineTick` 取场景 `endTick`。稳定标识为 `demandKey = "supply:<ruleId>"`、`id = "demand:supply:<ruleId>"`；同一规则在消费反复发生时只更新同一条需求，不新建重复需求。

开局校验：规则 ID 非空且唯一；source/dest 运输节点、owner actor 必须存在；source≠dest；target/consumption 为非负安全整数；两端节点库存必须属于 `ownerId`；同一 `ownerId`/cargo/dest 目标不得重复配置规则；生成的 demand ID/key 不得与既有实体/需求冲突。任一不满足即拒绝开局。

## 精确时间行为

每旬（settlement k-1→k，产物为状态 k）固定顺序：

1. 撤回可撤销承诺（既有）。
2. **生成/更新供应需求**：读取本旬开始时的目的地库存，加上所有属于规则所有者、状态为 `waiting`/`travelling`、且目的地与货物匹配的在途批次数量；缺口 `max(0, targetStock - 目的库存 - 在途预留)`。缺口为 0 且无既有需求时不建需求；有既有需求时把 `requested` 收敛为已交付/已预留/已取消之和，不再增发；有缺口时把 `requested` 提升为上述累计量加缺口。消费尚未发生，因此本步绝不预扣未来货物，也不把他主体的在途货算作本主体的补库。
3. 分层劳动分配（现含运输劳动预估与维护可负担检查）。供应需求在第 2 步已进入状态，因此本旬发运劳动可被预算。
4. 行动阶段迁移（既有）。
5. `beginWater`：入流（`seasonalInflow[(k-1)%36]`）、蒸散、灌溉。
6. `settleTransport`：推进既有在途、送达、派发新批次、过闸扣水/通行费。发货当旬不会瞬达。
7. **实际消费**：只有此时才读取运输结算后的目的地库存；按规则 ID 排序，逐条取 `min(consumptionPerTick, 目的地当前库存)` 扣减，库存永不为负。扣除量加入货物账本 `consumed`；不足部分不记为消费，也不生成货物。
8. 工程（既有，使用运输到货并已消费后的库存）。
9. 安全退出（既有）。
10. 农业（劳动 × 灌溉满足度）。
11. 维护财政支付（仅对有损伤河段，见限制）。
12. 河段临时关闭到期。
13. `finishWater`：超容量溢流（拓扑序，无出口则整旬回滚）。
14. 组装水/货账本。

因此消费在到达之后；但需求生成在下一旬消费之前，故本旬消费形成的补库需求最早下一旬生成，存在一个模型旬的补库延迟。这是明确的时间语义，不是漏算。

## 水量与物流（既有 T04 内容）

水量账本守恒：`期初 + 入流 = 期末 + 边界出流 + 消耗(蒸散+灌溉)`；节点间转移（过闸泄水、溢流）在总和内抵消，不计为全网消耗，也不在同一份水同时记为“消耗”与“下游增加”。过闸按实际通过批次扣水：`waterPerLoad × 批载` 从上游节点减、入下游节点（`toNodeId=null` 为边界出流）。有向水环在开局校验拒绝。

物流：需求派发量 `= requested - fulfilled - reservedInTransit - cancelled`；派发同时扣源库存并增 `reservedInTransit`，旅行旬数真实推进（派发旬不瞬达），送达转 `fulfilled`；途中损耗减少 `reservedInTransit` 使缺口恰好可补。重载经过限载边按 `shipClass = tighter(demand.loadClass, routeMinClass)` 拆成子批（`maxBatchSizeByClass`），保留 `parentId`。取消/到期批次先抵达下一安全节点，若该节点库存属需求所有者则转回其库存，否则就地持有（不传送到远处自有库存）。通行费 `costPerLoad × 批载` 由需求所有者支付给所在区域主体，仅在真实通行时发生；派发前按全路线通行费做可负担封顶。灾害/封航仅作用于相关边/批次。

## 隔离条件（新增真实机制导致的夹具调整）

- 维护财政是**预防性**付费：有维护劳动且 `maintenanceCost>0` 的运营河段无论有无损伤都逐旬计费；钱不足时欠费并逐旬累积损伤（非免费维护）。为保留既有回归，本轮把**施工中河段**（存在 `active` 且 `planned/construction/trial` 的工程）排除在常规维护计费之外——工程期间的养护由该工程承担。minimal 族 `cancel` 测试恰在河段上有施工中的疏浚工程，故无常规维护扣费、精确财政不变；reroute 测试只检查 `maintenanceCost` 字段（仍为 1）不受影响。这是显式隔离，非改期待躲失败。
- 供应规则默认空，故 minimal/peace/conscription/palace-and-canal/bottleneck 等旧夹具不产生新需求、消费或运输；G1 指标保持既有数值。
