Read-only review; no files changed. These 12 checks use the plan’s synthetic fixtures only and assert no historical event. Apply them as pass/fail gates when T01–T03 code exists.

## T01 — independent foundation exit
Refs: plan T01, `tests/core/determinism.test.ts`; architecture §3.3, §4, §5.1.

1. **Deterministic replay and input immutability.** Same scenario, seed, and tick sequence must produce equal `hashState`; `tick` must leave the input hash unchanged and return a distinct state; first tick yields `tick === 1`. Two `createGame` results must share no mutable arrays or objects. Directly test `rng.ts`: same seed gives the same sequence, weather/actor streams are separate, and core code uses no `Math.random`/`Date.now`. Fail if `tick` mutates its input or consumes a global RNG.

2. **Canonical state and hash.** The same state hashed in two fresh Node processes must match; JSON round-trip must preserve the hash. Changing only `rngStates`, `revision`, `pendingEvents`, `inTransit`, `appliedCommandIds`, a version, or populated `ending` must change the hash. Forbid `Map`/`Set` iteration-order dependence, `undefined` vs missing, `NaN`/`Infinity`, `-0`, unsafe integers, functions, and wall-clock/locale fields. Fail if key insertion order or JSON lossiness can hide a semantic difference.

3. **Tick/calendar boundaries.** `tick = 0` at start; settlement 0→1 yields 1; 35→36 rolls the year; 36 ticks/year as 12×3. A synthetic `effectiveTick = k` event must be absent after `k-1` and first present after `k`; test at least `k = 4`. Settlement 539→540 is the last playable one: `tick` at 540 returns the same state, empty events, unchanged hash, and no labor/production/consumption/RNG advance. Fail if the terminal tick is playable or events apply a tick early/late.

4. **Independent build and fixture factory.** T01 `src/core/index.ts` must have no runtime import of T02/T03 modules; the determinism test must pass with only T01 files present. `makeScenario('minimal')` must return a fresh deep copy each call, with the exact constraints: tick 0, `endTick` 540, regions a/b, link ab, sponsor central, one small dredge affordable, no disasters/population change, configurable seed. `createGame`/`tick` must not mutate the scenario. Keep lockfile and exact versions, strict `tsc --noEmit`, clean-install test run, and no imports from the old game. Fail if T01 depends on later files or fixtures are shared mutable singletons.

## T02 — exit / T03 entry
Refs: plan T02, `tests/core/projects.test.ts`; architecture §3.3, §4, §6.2.

5. **Envelope precedence and atomic failure.** Pin precedence: the documented order checks revision before duplicate ID, so the same `commandId` with a stale revision returns `STALE_REVISION`; with the current revision it returns `DUPLICATE_COMMAND`; neither may reapply or spend. New ID + stale revision → `STALE_REVISION`; bad target/time → `INVALID_TARGET`/`INVALID_TIME`. A failed command must preserve the exact `hashState`, revision, `rngStates`, `appliedCommandIds`, and `pendingEvents`, with no partial lock or project. A successful envelope advances revision once and is then stale; multiple events must not create multiple revision steps. A multi-reach command with one bad ID must fail all-or-nothing.

6. **Preview isolation and no future leak.** Repeated previews must leave the state hash unchanged, including nested commitments, RNG, and in-transit data. `PreviewResult` must contain no live references; mutating it must not change state; infeasible previews must return explicit infeasibility without throwing or changing state. A formal command after N previews must hash the same as one without previews. Perturb only formal `rngStates` (hidden future): feasibility, deterministic cost, and published bounds must remain unchanged; any sampling must use a preview stream. Fail if preview advances formal RNG or narrows bounds using actual future draws.

7. **`SET_PASSAGE` boundary matrix.** Schedule indices `-1`, `36`, non-integers, and duplicates → `INVALID_TIME`; an empty array means “never,” not “unrestricted”; all `0..35` are valid; input arrays must be copied. `closedUntil` equal to or earlier than `currentTick` → `INVALID_TIME`; `null` lifts immediately; `currentTick + 1` must be accepted. Document and test the inclusive/exclusive expiry boundary and exact restoration of the annual schedule. Temporary closure overrides the annual schedule; overlapping purpose windows resolve by `PassagePolicy`, not array order; `maxLoadClass` limits eligibility, not edge capacity. Unknown reach → `INVALID_TARGET`. Fail if closure never expires, expires a tick early, or load class silently reduces total capacity.

8. **Lifecycle transitions and completion gating.** Every status pair must be explicitly accepted or rejected; unknown project → `INVALID_TARGET`; illegal pair → `INVALID_PHASE`; a second pause/cancel with a distinct command ID must not double-reserve, double-refund, or duplicate liability. Pause keeps completed work but starts preservation/degradation; resume re-estimates current cost and schedule, not the original quote. Completion happens at tick end; new capacity starts next tick; trial passage is required; partial multi-reach completion enables only connected, qualified segments; paused/cancelled/completed projects consume no labor. Fail if completion immediately adds capacity or a double status command charges twice.

9. **Cancellation, liability, commitment conservation.** Cancel before start releases only unspent commitment, per sponsor, not pooled. Cancel after construction keeps completed work, moves the reach to pending disposal, and creates `PreservationLiability` with reachId, responsible party, minimum preservation request, and exit work; it persists while the project is `cancelled`. Reserve the minimum safety budget from unspent funds first, refund the remainder, record any shortfall, and never produce a negative refund. `SET_REACH_STATUS` mothballed/decommissioning must also carry minimum safety responsibility; `reroute` must link old-reach disposal and preserve old maintenance debt. The same locked funds cannot back two projects; per-sponsor locked/spent/refunded must reconcile; insufficient funds → `INSUFFICIENT_COMMITMENT` with gap and `relatedIds`; invalid sponsor → `INVALID_TARGET` with no partial project.

## T03 — exit / G1 entry
Refs: plan T03, `tests/core/labor.test.ts`; architecture §5.3, §6.1.

10. **Layered allocation exactness.** With 100 after life labor, agriculture 60, military 30, palace 20, and normal canal 20, allocation must be 30/60/5/5. Military 70 → agriculture 30, palace/canal 0; agricultural loss is attributed to mobilization and not backfilled. `palace-and-canal` requests of 80+80 against 100 must sum to ≤ 100 and cannot both receive 80; at least one is unmet. Test iterative cap redistribution: A requests 100 with cap 5, B requests 100, available 20 → 5/15, not 10/10. Integer remainder goes by largest remainder, then `activityId`; zero requests or zero pool must not divide by zero; allocated sum must not exceed capacity. Effective request must not exceed remaining work: a project with 1 work left cannot absorb 20; excess is redistributed to unmet same-tier requests or idles. Fail if weights move an activity across tiers or unused quota is silently reused.

11. **Cross-module quota and physical prerequisites.** Transport and maintenance requests must be estimated from current facilities and batches; actual use must not exceed allocated quota; unused quota idles and does not roll within the tick. No later module may append labor or bypass the ledger; project and actor rows need stable `activityId`/action IDs; the project module must not recompute allocation. Remote labor needs arrival delay and grain; no completed work before arrival; never counted at both source and destination. Funds and labor available but zero site grain must stall work with no negative stock; unused labor follows the explicit release rule. Fail if transport/maintenance overdraws or remote labor is credited immediately.

12. **Actors, population, burden, fixture isolation.** `peace` and `conscription` must differ only in the specified conscription; same seed, same forced-labor weights, births/deaths/migration off. Conscription effective at tick 3 for six ticks: absent at tick 2, active at states 3–8, absent at 9; after 9 ticks population must be equal, `projectWork` lower, burden higher, and `laborAllocated ≤ laborCapacity`. Burden must derive from actual intensity/duration and recover gradually; conscription must never subtract population; population changes only through explicit events. `proposed`/`mobilizing` consume no labor; `active` does; cancel before active releases the future request but not consumed labor or accrued burden; a warning precedes occupation; one stable action ID must link war labor and later demand. Fail if conscription reduces population, burden resets instantly, or a duplicate war/action entity is created.
